Loop · Creator Hub · first design pass · 2026-09-22

One business, two seats: the creator's and EMG's, over the same objects

Creator Hub is the environment where a creator and EMG run the creator's business together. This pass defines the product and the experience — both the creator seat and EMG's Creator Operations seat — grounded in what Loop already is. It designs nothing that would become a second authority. Where today's backend cannot support a screen, the gap is named, not invented around.

StatusDesign definition for approval. Nothing built.
ShapeOne Loop shell · two authorized projections
AuthoritiesCRM · Work OS · Brain · Storage · Loop meaning
New creator conceptsContent · Asset/Version · Deliverable · Earnings ledger · Social evidence
The one rule that shapes everything below: the creator and EMG never look at two copies. They look at the same Opportunity, the same Work, the same Version chain, the same ledger row — through different authorized projections with different actions. Synchronization is a property of sharing the object, not a process.
Section 1

What Creator Hub is, and where it sits in Loop

Loop is an AI-first operating system for customer-facing businesses; the CRM, Work OS, Brain and the source connections are its organs. EMG's creator business is one such business, and the creator is its most important external participant. Creator Hub is therefore not a module beside CRM or Work — it is a participant projection: the set of surfaces, states and actions Loop composes for a person whose participation is "managed creator", plus the internal surfaces EMG uses to operate that creator. This is exactly the direction the UI architecture record already states ("responsive projections composed for a participant according to identity, membership, participation, and permissions") and it keeps decision C-02's line: no second Creator application, no second Opportunity, task, campaign or intelligence system.

The creator should be able to answer eight questions without understanding any of that: what's happening, what's developing, what EMG needs from me, what am I working on, where is it in production, how did the published work do, what is Loop learning about what works for me, and what have I earned versus what I can actually move. EMG should be able to answer the mirror image for each creator and across all creators: what needs us, what needs them, what is due, what is in production, what is performing, what is owed.

Seven areas, exactly as briefed: Home · Opportunities · Content · Analytics · Tasks · Earnings · Profile. They live in the one Loop shell under the transitional root /app/creator/…, listed in LOOP_NAV as a group offered only to the creator authority — the same registry, filtered, never a second menu.

Mobile: the fixed five-area bar

Loop's mobile shell puts five operating areas in a fixed bottom bar. The creator's five are the five things a thumb reaches for daily: Home · Content · Opportunities · Tasks · Earnings.

Section 5

Primary creator journeys

Each step names the authority that changes, so the journey is also a proof that no step needs a second system.

J1 · Review and approve an edit

  1. Home → "Review EMG Edit v2 — ready" WorkItem ← Work stage event
  2. Opens the Content record on the v2 version Content / Version
  3. Plays v2; toggles Compare to Original at the same timestamp Version chain
  4. Approve → v2 becomes Approved Final; the Work stage completes; the WorkItem resolves Content · Work OS · WorkItem
  5. If a Deliverable is linked, it is marked fulfilled by v2 Deliverable (creator domain)

J2 · Request an edit

  1. Content → Request an Edit (or from any raw Content's actions)
  2. Source: pick an existing Version or upload new Storage + Version
  3. Instructions, references (Versions or links), optional Campaign/Deliverable Content associations
  4. Requested return: date and time requested turnaround (Work OS field, new)
  5. Submit → a WorkInstance from the Editing blueprint, stage Submitted, creator visible Work OS
  6. EMG sets expected turnaround → reflected on the request and on Tasks/Upcoming Work OS

J3 · Request changes and receive the next version

  1. From Edit Review → Request changes (notes, optional timestamped points)
  2. The same Work reopens: stage Creator Review → Changes Requested → Editing Work OS stage events
  3. Editor uploads v3 against the same chain; stage → Creator Review Version · Work OS
  4. Creator gets "v3 ready for review" — the same WorkItem re-detected, never a duplicate

J4 · Opportunity to confirmed campaign to tasks

  1. Home shows a new Active Opportunity at "Brand interest" CRM Opportunity (creator-visible projection)
  2. EMG moves it through Pitching / Negotiating internally; the creator sees only designated states and updates
  3. Confirmed → EMG creates a Campaign and declares Deliverables CRM Campaign · Deliverables
  4. Deliverables appear as Tasks/Upcoming with due dates; each links to a Content slot
  5. Upload deliverable → Request an Edit if needed → approve → fulfilled

J5 · Publish, perform, learn

  1. Approved Final → creator marks it published and connects the post (platform, url) Published Version
  2. Performance attaches from the connected platform social evidence
  3. Analytics reflects it; tapping the spike opens the Content record
  4. Brain produces a Finding about this creator from eligible evidence Decision Engine
  5. Home / Content / Analytics show the finding with "View evidence"

J6 · Get set up, get paid

  1. Home "Things that need you": Connect Instagram · Complete payout setup setup prompts derived from Profile state
  2. Profile → Social accounts → connect (provider consent) creator connection
  3. Earnings shows Expected as campaigns confirm; Pending as they complete; Received; then Available once an authorized EMG user releases ledger
  4. Transfer funds → provider transfer → Transfer pending → Paid payout provider

Thumb-zone rules

  • The one primary and one secondary action of a screen live in a sticky bottom bar above the five-area bar (Approve / Request changes; Upload; Transfer).
  • Destructive or money-moving actions confirm in a sheet, never a modal dialog.
  • Lists are cards with a thumbnail, a state pill and one line; a long-press is never required.
  • Filters are horizontal chips under the page title; sorting is implicit (recency, due).

Media-first review

  • The player is the page; metadata sits under it, actions under the thumb.
  • Compare is a segmented control (Original · v1 · v2) that keeps the playhead — same moment, different version.
  • Request changes opens a sheet over the paused frame; "Add a note at 0:11" captures the timestamp.
  • Approve shows a one-line consequence ("This becomes the final for the Kona deliverable") before confirming.

Upload

  • Full-height sheet; the file picker opens immediately; progress is a ring on the card in the library while it uploads.
  • Name, campaign/deliverable and "request an edit right after" are optional follow-ups, not gates.
  • Large videos: background upload with a persistent card state Uploading → Processing → Ready; failure shows a Retry on the card.

Tasks and notifications

  • A task row opens the object where the action belongs — never a task detail page.
  • Push/email notifications deep-link the same way (Review v2 → the Version view).
  • Completed tasks are read-only history with the object link preserved.

Analytics on a phone

  • One number per card, sparkline, delta; platform chips; window chips.
  • Tapping a spike opens a sheet listing the Content published in that window; tapping one opens the record.
  • Intelligence explanations sit under the chart as one-line findings with "Evidence".

Desktop adaptation

  • Records use RecordLayout: main column (preview, versions) plus a rail (context, actions, intelligence).
  • Version comparison side by side with a shared scrubber.
  • Library becomes a denser grid with a list toggle; Analytics gets full charts and a table of top content.
  • Nothing is desktop-only except density; every action exists on the phone.
Section 8

Area by area: hierarchy, intelligence, states, transitions

Home — the 10-second snapshot

Hierarchy
Greeting → four numbers (Total audience, 30-day growth, Active opportunities, Available balance) → Things that need you → Active opportunities → Content in progress → Latest intelligence.
Sources
Numbers: social evidence, CRM projection, ledger. Needs you: Work OS assignments/stages due to the creator + creator-private WorkItems + setup prompts derived from Profile (unconnected platform, incomplete payout) — no Home task system. Opportunities: CRM projection. In progress: Content with an active Work. Intelligence: the newest accepted-or-proposed Finding with evidence.
Intelligence
One finding, one CTA ("View evidence →" opens the Finding's evidence drawer). Never a score.
Empty / loading / error
No connected platform: the audience tile says "Connect a platform to see your audience" and links to Profile. No opportunities: "No active opportunities — EMG will add them here." No balance: "No earnings yet" — never $0 dressed as data. Each panel loads and fails on its own (Loop's settle pattern): a panel that cannot read says so; Home never goes down with it.
Transitions
Every row is a link to its object: a Needs-you row → the Version view / the Deliverable / Profile; an opportunity → its record; content → its record; the number tiles → Analytics / Opportunities / Earnings.

Opportunities

List
Grouped by creator-visible state (§9.4), newest change first; each card: brand (as designated), campaign name if one exists, state pill, next thing for the creator if any.
Detail
Overview (what it is, in EMG's creator-facing words) → Campaign (state, dates) → Deliverables (type, due, status, linked Content) → Timeline (designated transitions and creator-visible updates only) → Files (Versions designated as shared: briefs, references) → Your tasks → Production (Work in progress) → Payment (the ledger's view for this campaign) → Updates.
Intelligence
Where a campaign has published content: commercial-performance context ("sponsored posts using your recurring-character format close most of the gap") with evidence; never forecasts, never internal assessments.
States
Empty: "Nothing developing yet." Loading skeleton. A creator can never see an Opportunity not designated for them: not-found, not forbidden.

Content — library and record

Library
Visual grid of Content cards (latest Version thumbnail, name, state pill, campaign chip, platform badge if published, performance number if published). Chips: All · Videos · Photos · Campaigns · In production · Published. Two actions: Upload, Request an Edit.
Record
Preview → Status (Raw → Editing → Review → Approved → Published) → Context (Campaign, Opportunity, Deliverable, Work) → Versions → Intelligence → Performance → state-dependent actions.
Intelligence
Pre-publish: findings comparing this content to the creator's own history (facts and observations from version metadata and any governed content-feature evidence). Post-publish: what happened versus the pattern, and version-change findings ("shortening the opening preceded a +12% completion versus your baseline" — only when the evidence supports it). Each finding shows Fact / Observation / Interpretation / Recommendation and its evidence rows with limitations.
States
Empty library: "Your content lives here. Upload your first video." Uploading / Processing / Ready card states. Failed upload: Retry on the card. A version whose bytes are unavailable shows the metadata and says so.

Request an Edit

Flow
Source → Instructions → References → Context & requested return → Submit. Four sheet steps; each is one screen on a phone with a progress dots row.
Turnaround
Two distinct fields the creator always sees side by side: Requested (theirs) and Expected (EMG's, set after review; blank shows "EMG will confirm a return time"). Later, service-level defaults can pre-fill Expected for EMG to adjust.
After submit
Lands on the Content record's Production section showing Submitted with the requested time; a task appears in Upcoming.

Analytics

Hierarchy
Platform chips (All · TikTok · Instagram · YouTube · Facebook) and window chips (7D · 30D · 90D · 1Y) → summary tiles (audience, growth, views, reach, engagement, posting frequency) → chart → top content → platform comparison.
Connection to Content
Every point, bar and top-content row resolves to Published Versions; tapping opens the Content record. Analytics provides evidence, Intelligence interprets it, Content is the object.
Intelligence
Findings that explain a change in the selected window ("this spike is one post" / "posting frequency fell"), each with evidence; a Feed Analysis link for the deeper pattern view.
States
No platform: connect prompt. Platform connected but no data yet: "Reading your last 90 days — usually a few minutes." Partial platforms: a PartialDataNotice naming which are missing.

Tasks

Views
Needs attention (due to the creator now) · Upcoming (due later, expected returns) · Completed.
Sources
Work OS: stages assigned to the creator (review, approve, upload deliverable). WorkItems: creator-private detections. Setup: derived prompts. Deliverables: due dates.
Rule
A task is a pointer with a due date and a verb; it opens the object. No task detail, no task management.

Earnings

Hierarchy
Available balance (the only big number) → Transfer funds → Expected · Pending · Available · Paid YTD → campaign/transaction history → each row opens the Campaign Payment Detail with the trace Opportunity → Campaign → Deliverable → payment event.
Rule
Expected and Pending are never styled as money you can move: muted, labelled "not yet payable", no button near them. Only Available carries the transfer action.
States
No earnings: "No earnings yet — confirmed campaigns will appear here as Expected." Payout not set up: the Transfer button is replaced by "Set up payouts". Provider unavailable: an honest unavailable state, balance still shown.

Profile

Sections
Creator information · Profile · Social account connections · Content categories · Audience · Commercial/rate information (only fields EMG designates) · Payout setup · Documents · Notifications · Preferences.
Rule
Every field is labelled by its owner: creator-editable, EMG-maintained (read-only with "Ask EMG to change"), or system-derived (read-only with its source). Identity fields come from the CRM Person; the creator edits creator-domain attributes only.

9.4 Opportunity: creator-visible states over CRM's locked shape

Section 12

How both seats stay synchronized

The principle

Both seats are read models over the same rows. A creator's "Review v2" and an editor's "awaiting creator" are the same WorkStage row read with two projections. There is nothing to reconcile because there is nothing duplicated.

What would break it (forbidden)

  • A creator-side "project" or "request" table beside Work OS.
  • A creator-side opportunity status stored on the creator's record.
  • Copying performance numbers onto Content or Campaign fields.
  • A Home task list that is not a projection of Work OS, WorkItems and derived setup state.
  • An "admin copy" of the version chain, or a version that is overwritten in place.

Section 15

Decisions to resolve before mockups

  1. Creator access. C-02 (2026-09-15) says external participant authentication, memberships and portals are not authorized; this brief requires a creator-facing seat. Recommendation: amend C-02 for one participant type — the managed creator — as an external participant of EMG's organization with creator-scoped authority, keeping "no multi-org sign-in" and "no second application". Everything else in this document depends on it.
  2. Mobile bar composition. Recommendation: Home · Content · Opportunities · Tasks · Earnings, with Analytics one tap from Home and Content and Profile on the avatar. Alternative: swap Tasks for Analytics and rely on Home's "Things that need you" — weaker for creators with many deliverables.
  3. Creator-domain nouns. Approve Content, Version, Deliverable, Earnings ledger, Social connection and Performance evidence as the concepts Creator Hub deliberately establishes; confirm Deliverable is hosted on the CRM Campaign record but owned by the creator domain, as the CRM readiness record already implies.
  4. Opportunity visibility mapping. Approve the model: creator-visible state is a declared mapping in the organization's stage set; unmapped stages never show; internal information never inherits. Confirm whether "Didn't go ahead" is ever shown.
  5. Earnings vocabulary and release authority. Confirm the six states and their names, who may release (Owner/Admin, or a finance role), and whether "Received by EMG" is creator-visible or collapses into Pending.
  6. Turnaround defaults. Whether a service-level default (24–48 h) pre-fills Expected on submission, or Expected stays blank until a person sets it. Recommendation: blank until set, defaults as the second step.
  7. Platforms in scope for v1 evidence. Which of TikTok, Instagram, YouTube, Facebook connect first; this bounds Analytics and every performance-based finding.
  8. Intelligence scope for v1. Which features are computable from evidence without a model (length, version diffs, posting time, platform, organic/sponsored) versus which need a governed content-feature task (people, animals, products, hooks, tone). Recommendation: ship the evidence-only findings first; they are defensible immediately.
  9. Notifications. Whether creator notifications (push/email) are in the first release; the design deep-links assume they exist eventually.
  10. Managers and multiple creators. Whether a creator's manager or a multi-creator household signs in as the creator, as a delegate, or not at all in v1. Recommendation: not in v1.
  11. Publication linkage. Whether the creator marks and connects published posts by hand, or connected platforms detect them. Recommendation: by hand first, detection later.
